# LaevaBangumi 番剧资源映射重构设计

> 日期：2026-07-24
>
> 范围：新 Bangumi 元数据域与新 ResourceSource 数据域之间的映射、自动匹配、放送日触发、人工 XLSX 审核和映射排除关系。
>
> 非范围：旧表迁移、旧映射兼容，以及公开 Detail、Updates、Play API 对新映射和新分集表的消费。

## 1. 目标

本次重构建立一套精简、稳定、解耦、内聚的番剧资源映射机制：

- `bangumi_subjects` 是 Bangumi 番剧事实来源。
- `source_items`、`source_item_aliases`、`source_episodes` 是采集站资源事实来源。
- 映射域只表达 Bangumi ID 与采集站条目之间的关系，不复制标题、评分或运行状态。
- 自动匹配只操作本地数据库，不直接请求 Bangumi 或采集站。
- 自动匹配只创建一对一映射；分段映射完全由人工决定。
- 不对所有未映射番剧进行长期定时重试。
- 人工操作通过服务端 XLSX 导出、修改和导入完成，不增加后台管理 HTTP API。
- 不迁移、不读取、不双写旧 `resource_mappings`、`retry_state`、`manual_resource_state` 等表。

## 2. 非目标

- 不在映射表中保存匹配评分、命中标题、来源、备注或偏移量。
- 不创建通用的 `wait`、`no_resource` 状态表。
- 不保存自动匹配失败次数或下一次重试时间。
- 不使用 AI、外部语义服务或在线分词服务进行自动匹配。
- 不自动推断或修改分段区间。
- 不在本阶段切换公开播放与更新 API。
- 不修改客户端。

## 3. 数据模型

映射域使用三张职责单一的表。

### 3.1 `bangumi_resource_mappings`

```sql
CREATE TABLE bangumi_resource_mappings (
  bangumi_id INTEGER NOT NULL,
  source_key TEXT NOT NULL,
  source_item_id TEXT NOT NULL,
  source_episode_start INTEGER,
  source_episode_end INTEGER,
  PRIMARY KEY (bangumi_id, source_key),
  FOREIGN KEY (bangumi_id)
    REFERENCES bangumi_subjects(bangumi_id),
  FOREIGN KEY (source_key, source_item_id)
    REFERENCES source_items(source_key, source_item_id),
  CHECK (
    (source_episode_start IS NULL AND source_episode_end IS NULL)
    OR
    (
      source_episode_start >= 1
      AND (
        source_episode_end IS NULL
        OR source_episode_end >= source_episode_start
      )
    )
  )
);

CREATE INDEX idx_bangumi_resource_mappings_source_item
  ON bangumi_resource_mappings(source_key, source_item_id);
```

映射表只保存五个业务字段。`source_item_id` 使用文本类型，以支持非数字采集站 ID。

#### 区间语义

| 始集 | 末集 | 语义 |
|---|---|---|
| 空 | 空 | Bangumi ID 与采集站 ID 一对一映射 |
| 正整数 | 正整数 | 包含始末集的已完结分段 |
| 正整数 | 空 | 从始集开始、仍在放送的最后一个分段 |
| 空 | 正整数 | 非法 |

分段播放时，每段从第 1 集重新编号：

```text
display_episode_index = source_episode_index - source_episode_start + 1
```

映射表不保存偏移字段。

### 3.2 `auto_match_schedule`

```sql
CREATE TABLE auto_match_schedule (
  bangumi_id INTEGER NOT NULL,
  source_key TEXT NOT NULL,
  eligible_on TEXT NOT NULL,
  PRIMARY KEY (bangumi_id, source_key),
  FOREIGN KEY (bangumi_id)
    REFERENCES bangumi_subjects(bangumi_id)
);

CREATE INDEX idx_auto_match_schedule_eligible
  ON auto_match_schedule(eligible_on, source_key, bangumi_id);
```

该表只保存未来完整放送日期的一次性匹配触发。`eligible_on` 必须是有效的 `YYYY-MM-DD`。

它不表示业务状态，也不保存失败次数、错误、`wait` 或 `no_resource`。

### 3.3 `auto_match_exclusions`

```sql
CREATE TABLE auto_match_exclusions (
  bangumi_id INTEGER NOT NULL,
  source_key TEXT NOT NULL,
  source_item_id TEXT NOT NULL,
  PRIMARY KEY (bangumi_id, source_key, source_item_id),
  FOREIGN KEY (bangumi_id)
    REFERENCES bangumi_subjects(bangumi_id),
  FOREIGN KEY (source_key, source_item_id)
    REFERENCES source_items(source_key, source_item_id)
);

CREATE INDEX idx_auto_match_exclusions_source_item
  ON auto_match_exclusions(source_key, source_item_id);
```

该表只表示：双方当前均空闲，但这一对 ID 已被人工否定，禁止自动重新匹配。

它不保存原因、时间或历史记录。

## 4. 映射不变量

### 4.1 一对一映射

- 同一个 `(bangumi_id, source_key)` 最多一条映射。
- 始末集均为空的一对一映射必须独占对应 `(source_key, source_item_id)`。
- 自动匹配只能创建一对一映射。
- 自动匹配要求 Bangumi ID 与采集站 ID 两端都没有映射。
- 自动匹配不能删除、替换或修改任何已有映射。

### 4.2 人工分段映射

- 同一个采集站 ID 可以人工映射到多个 Bangumi ID。
- 一旦同一采集站 ID 对应多个 Bangumi ID，所有映射都必须填写始集。
- 分段区间允许存在空档，用于跳过总集篇、特别篇或错误资源。
- 分段区间禁止重叠。
- 最多存在一个末集为空的开放分段。
- 开放分段必须是起始集最大的最后一段。
- 分段边界完全由人工写入，服务端不自动推断。

### 4.3 人工写入权威性

- 人工写入可以建立一对一映射或分段映射。
- 人工写入分段时，如果目标采集站 ID 被一条一对一映射占用，在同一事务中删除旧一对一映射后再写入分段。
- 如果目标采集站 ID 已有其他分段，保留它们并校验导入后的最终区间集合。
- 人工写入仍必须引用存在的 Bangumi ID、采集站和采集站 ID，并满足所有区间不变量。

### 4.4 跨行约束的实现边界

SQLite 行级 `CHECK` 只负责单行合法性。以下跨行约束统一由 `mappingRepository` 在事务内校验：

- 一对一独占。
- 分段不重叠。
- 开放分段唯一且位于最后。
- 人工覆盖旧一对一映射。
- 自动匹配写入前的双端空闲检查。
- 排除关系的写入与清理。

任何调用方都不能直接写映射表。

## 5. 排除关系生命周期

### 5.1 人工删除

人工删除、替换或分段批量修改必须先计算整次操作提交后的最终状态，再决定是否建立排除关系：

- 如果原 Bangumi ID 在同一采集站已经建立新映射，不写排除关系。
- 如果原采集站 ID 仍被其他分段占用，不写排除关系。
- 只有原 ID 对被删除且双方在最终状态中都为空闲，才写入原 ID 对的精确排除关系。
- 在一个事务中修改同一 ID 对的分段区间属于替换，不生成排除关系。

这样可以阻止刚被人工否定的错误关系再次由自动匹配建立。

### 5.2 建立新映射

任意映射成功写入后，在同一事务中清理已经失效的排除关系：

- 删除该 `(bangumi_id, source_key)` 下的所有排除关系。
- 删除该 `(source_key, source_item_id)` 关联的所有排除关系。

因此排除表不会残留某一端已被其他映射占用的过时信息。

### 5.3 自动与人工权限

- 所有自动匹配在写入前必须检查精确排除关系。
- 人工写入不受排除关系限制。
- 人工重新建立被排除的 ID 对时，成功写入后自然清除该排除关系。

## 6. Bangumi 详情补全

Calendar 和搜索只负责发现番剧及持久化摘要，不能直接触发自动写入映射。

```text
Calendar / 搜索摘要入库
→ 为每个有效 Bangumi ID 登记详情补全
→ 异步详情队列去重、限速获取 Subject 详情
→ 详情事务成功
→ 协调放送资格和自动匹配
```

### 6.1 绝对前提

只有 `bangumi_subject_refresh_state.last_succeeded_at` 已存在，即至少成功完成一次详情补全，番剧才允许参与自动匹配。

即使 Calendar 或搜索摘要看起来已经包含足够字段，也不提前匹配。

详情补全提供：

- 完整或更精确的 `air_date`。
- 中文名、原名和 infobox 别名。
- `platform`。
- `eps`、`total_episodes`。
- 后续自动匹配需要的完整名称池。

### 6.2 队列行为

- Calendar 和搜索返回的所有有效番剧都登记详情任务，包括尚未放送的番剧。
- `bangumi_subject_refresh_state` 对同一 ID 去重。
- 继续采用现有详情队列的限速、并发、短时请求重试和失败退避。
- 详情请求失败时不进行资源匹配。
- 已完成详情的番剧继续按现有每周周期刷新。

### 6.3 详情写入后的通知

Bangumi 模块在详情事务成功后调用注入的：

```text
onDetailPersisted(bangumiId)
```

Bangumi 模块只发送事实变更通知，不导入具体匹配算法。

## 7. `air_date` 规范与放送资格

### 7.1 唯一规范字段

Bangumi 外部接口字段统一映射为：

```text
calendar.air_date  ─┐
search.date         ├─→ domain.airDate ─→ bangumi_subjects.air_date
detail.date        ─┘
```

数据库不另存 `date` 字段。

### 7.2 有效日期覆盖

- 有效新日期覆盖旧值。
- 缺失、空字符串、`0000-00-00` 或其他无效值不能清除已有有效日期。
- 无效值不能降低已有日期精度。
- 只有收到另一个有效日期时才更新已有有效值。

详情全量替换同样遵守该规则，不能因为响应缺少日期而写入 `NULL`。

### 7.3 上海自然日判断

所有放送资格判断使用 `Asia/Shanghai` 当天的自然日期，不把 `air_date` 转换为 UTC 时间点。

支持三种有效精度：

| 格式 | 判断规则 |
|---|---|
| `YYYY-MM-DD` | 小于等于上海当天则已放送；未来则建立精确计划 |
| `YYYY-MM` | 早于当前上海年月则已放送；当前或未来年月无法确认 |
| `YYYY` | 早于当前上海年份则已放送；当前或未来年份无法确认 |

不完整且无法确认已经放送的日期：

- 不参与匹配。
- 不进入计划表。
- 不增加额外扫描任务。
- 等待后续每周详情刷新获得更精确日期，允许最多约一周延迟。

### 7.4 元数据更新后的协调

每次 Bangumi 摘要或详情成功持久化后，资格协调器读取数据库最新事实并幂等处理。尚未成功完成过详情补全时，协调器只保留摘要并等待详情任务，不建立计划或执行匹配；已有 `last_succeeded_at` 后才应用以下规则：

- 已有映射：删除无用计划，不匹配。
- 精确未来日期：插入或更新计划。
- 精确日期提前到今天以前：删除计划并立即尝试本地匹配。
- 精确日期推迟：更新计划日期。
- 日期变成无法判断的不完整值：删除原计划。
- 已能确认放送的不完整日期：删除计划并立即尝试本地匹配。
- 缺失或无效日期：不匹配、不计划。

Bangumi 元数据更新不会自动删除或修改已有映射。

## 8. 一次性放送计划

### 8.1 建立计划

只有满足以下条件的番剧才建立计划：

- 已完成至少一次详情补全。
- `air_date` 是未来的完整 `YYYY-MM-DD`。
- 指定采集站尚无映射。

### 8.2 执行计划

- 每天在 `Asia/Shanghai` 零点后处理 `eligible_on <= 今天` 的计划。
- 服务启动时同样补处理已到期计划，避免停机跨过放送日造成遗漏。
- 执行前重新读取 Bangumi 详情状态、最新 `air_date`、映射和采集站初始化状态。
- 采集站未完成首次初始化或数据库异常时保留计划。
- 完成一次有效的纯数据库匹配尝试后删除计划。
- 没有候选或未达到自动门槛时也删除计划，等待采集站增量更新反向触发。

计划表不是长期重试队列。

## 9. 自动匹配触发

自动匹配采用双向事件触发，不周期性遍历所有未映射番剧。

### 9.1 Bangumi 正向触发

触发来源：

- 首次详情补全成功。
- 后续详情刷新成功。
- 精确放送计划到期。
- 不完整日期更新后已经足以确认放送。

处理一部满足资格且尚未映射的 Bangumi 番剧，在本地资源表中寻找候选。

### 9.2 采集站反向触发

触发来源：

- 采集站详情首次成功。
- 主标题变化。
- 别名集合变化。
- 年份变化。
- 分集数量变化。

对于每个变化的采集站 ID：

- 如果已有任意映射，立即跳过。
- 如果详情不完整或没有分集，立即跳过。
- 否则从已完成详情、已放送、尚未映射的 Bangumi 番剧中召回候选。

初始化和增量更新由资源域报告本次可用于匹配的采集站 ID，调度器再通知映射运行时。FFZY 子模块不导入 Bangumi 或映射仓库。

### 9.3 首次全量初始化

采集站首次全量初始化完成后，从符合资格且尚未映射的 Bangumi 番剧一侧进行一次协调。

不对全部采集站 ID逐条反向扫描全部 Bangumi 条目。

### 9.4 网络边界

自动匹配只能读取本地：

- `bangumi_*` 元数据表。
- `source_*` 资源表。
- 三张映射域表。

自动匹配不能调用 Bangumi Client、FFZY Client 或其他网络接口。

## 10. 候选硬过滤

候选必须依次通过以下过滤。

### 10.1 基本资格

- Bangumi 已完成至少一次详情补全。
- Bangumi 已确认开始放送。
- Bangumi ID 在该采集站尚无映射。
- 采集站已完成首次全量初始化。
- 采集站条目已有详情和至少一条 `source_episodes`。
- 采集站 ID没有任何映射。
- ID 对不在排除表。

### 10.2 年份

- Bangumi 年份取规范化 `air_date` 的年份。
- 采集站年份取 `source_items.year`。
- 双方年份有效且相同：继续。
- 双方年份有效但不同：拒绝自动匹配。
- 任意一方缺少年份：只有至少一对完整名称规范化后完全相等才允许继续。
- 人工映射不受年份限制。

### 10.3 季度

- 双方明确季度且相同：继续。
- 双方明确季度但不同：拒绝。
- 只有一方明确季度：不直接拒绝，继续依赖年份、名称、集数和双向唯一性。
- 同年出现多个无法区分的同系列季度时，因候选不唯一而不自动写入。

### 10.4 Part / Cour

- 双方明确 Part/Cour 编号且相同：继续。
- 双方明确编号但不同：拒绝。
- 只有一方明确 Part/Cour：不自动映射，转人工。

Part/Cour 不对称比普通季度不对称更容易表示分段资源，因此采用更严格规则。

### 10.5 作品形态

结构化提取：

- 剧场版 / movie。
- OVA / OAD。
- 特别篇 / SP / special。
- 其他双方都能明确识别的强形态。

规则：

- 双方明确形态且冲突：拒绝。
- 只有一方带形态标记：不直接拒绝，继续综合年份、完整名称、`platform`、集数和双向唯一性。
- `总集篇`、`recap` 保留为正式标题语义，不作为采集站多季度合并标记。
- `合集`、`全集`只生成去噪比较变体，不用于判断多季度合并。

### 10.6 分集数量

- Bangumi `total_episodes` 有效且采集站当前分集数大于它：拒绝自动一对一映射。
- 采集站分集数小于或等于 Bangumi 总集数：允许继续，因为资源可能仍在连载。
- Bangumi 总集数未知：不使用分集数量过滤。
- 分集数相同不额外加分，避免把巧合作为证据。
- 人工映射不受该过滤限制。

多季度合并资源通常不带“合集”等字样，主要通过分集溢出和人工分段机制处理。

## 11. 名称池与规范化

### 11.1 分级名称池

Bangumi 名称来源：

- `name_cn`。
- `name`。
- infobox 中的别名、中文名、日文名、原名、罗马字和放送译名。

采集站名称来源：

- `source_items.title`。
- `source_item_aliases.alias`。

优先级：

- Bangumi 中文名与采集站主标题权重最高。
- 主名称之间的完整相等是最强证据。
- 正式名称或别名之间的完整相等也是强证据。
- 模糊匹配中主标题权重高于别名。
- 别名数量不累计加分，只取最可信的一对名称。
- 弱模糊别名不能覆盖主标题的结构化冲突。

### 11.2 无损规范名称

规范化只用于匹配计算，不改写数据库原值：

1. 解码 HTML 实体。
2. Unicode NFKC 全半角统一。
3. 大小写统一。
4. 空白和标点统一。
5. 使用本地 OpenCC 繁体转简体转换生成比较值。
6. 删除“更新至 N 集”“完结”“HD”等明确采集站噪声。

`总集篇`、`recap` 等正式作品语义不能被当作噪声删除。

### 11.3 比较变体

每个名称保留完整规范版本，并额外生成安全比较变体：

- 独立出现或位于标题末尾的罗马数字生成阿拉伯数字变体。
- `第二季`、`第2期`、`Season 2` 等提取为 `season=2`。
- `第2部分`、`Part 2`、`第2クール` 等提取为 `part=2`。
- `合集`、`全集`可生成去噪变体，但原始规范名称仍保留。
- 普通标题中的汉字数字不转换，例如“一念永恒”“十万个冷笑话”。

季度和 Part/Cour 语义独立提取，但不从完整名称中永久删除。

### 11.4 系列核心名

系列核心名只用于扩大召回范围：

- 可以去掉已结构化提取的季度、Part/Cour 和通用形态词。
- 不能单独作为自动写入依据。
- 最终必须至少有一对完整名称达到自动名称门槛。

## 12. 名称评分与双向唯一性

### 12.1 确定性评分

完整名称对使用本地确定性信号评分：

- 规范化完全相等。
- 一方包含另一方时的覆盖比例。
- 中文连续片段覆盖。
- 字符 n-gram 重合度。
- 编辑距离相似度。

年份、季度、Part/Cour、作品形态和分集数量是前置过滤，不通过加减分掩盖明确冲突。

### 12.2 初始门槛

```text
最低名称得分：0.80
Bangumi → 采集站第一、第二名最小分差：0.15
采集站 → Bangumi 第一、第二名最小分差：0.15
```

任一方向不存在第二候选时，只检查最低名称得分。

阈值集中定义在映射配置模块，不写入数据库。

### 12.3 双向唯一最佳

自动写入必须同时满足：

```text
该采集站 ID 是此 Bangumi ID 的唯一明显最佳候选
并且
该 Bangumi ID 也是此采集站 ID 的唯一明显最佳候选
```

任一方向候选不唯一、分差不足或结构化语义不明确，都不自动写入。

### 12.4 当前数据库初评

对当前 `data/anime.db` 的只读评估结果：

- 111 部 Bangumi 番剧。
- 100 部按 2026-07-22 已到放送日期。
- 5411 个 FFZY 条目已有详情和分集。
- 当前新 Bangumi 条目尚未完成详情补全，infobox、总集数等数据为空。
- 在该受限名称池下，`0.80 + 双向分差 0.15 + Part/Cour 不对称转人工` 约接受 59 对，人工抽查未发现明显错误。

该结果只用于确定保守初值。首次详情补全获得完整名称池和总集数后，必须再做一次只读评估，才能决定是否调整阈值。

## 13. 自动匹配结果

自动匹配成功只写入：

```text
bangumi_id
source_key
source_item_id
source_episode_start = NULL
source_episode_end = NULL
```

不保存：

- 匹配评分。
- 命中的 Bangumi 名称。
- 命中的采集站名称。
- 自动或人工来源。
- 备注。
- 失败原因。

写入事务内再次检查：

- Bangumi 端仍空闲。
- 采集站端仍空闲。
- ID 对仍未被排除。

并发导致条件变化时返回 `skipped`，不覆盖任何映射。

## 14. 未自动映射原因

失败原因不持久化。人工导出时根据最新数据库事实和当前算法实时计算。

对每部番剧输出一个简明的当前原因，例如：

- 尚无可用资源。
- 名称相似度不足。
- 候选不唯一。
- 年份冲突。
- 季度冲突。
- Part/Cour 信息不明确。
- 作品形态冲突。
- 采集站分集数超过 Bangumi 总集数。
- 候选已被人工排除。

如果存在多个阻止因素，按自动匹配流水线中最先形成最终拒绝结论的因素输出，保证一行只显示一个稳定、易读的原因。

不提供按原因筛选。

## 15. XLSX 人工审核

### 15.1 命令

```text
npm run mapping -- export [--source <key>] [筛选参数] [--output <path>]
npm run mapping -- import <path>
```

- `--source` 指定采集站。
- 未指定时使用资源源注册表中的首个采集站。
- 每个工作簿只处理一个采集站。
- 导入时从工作簿元数据读取采集站，无需再次指定。
- 使用服务运行时可用的 XLSX 库生成和解析工作簿；工作簿实现封装在 `mappingWorkbookService`。

### 15.2 导出筛选

```text
--name <番剧名称包含词>
--year <Bangumi 放送年份>
--bangumi-id <Bangumi ID>
--limit <Bangumi 条目数量>
--include-upcoming
```

- 默认只列出已完成详情、已确认放送且尚未映射的番剧。
- `--include-upcoming` 额外列出尚未放送或日期尚不足以判断的番剧。
- 不生成采集站候选。
- 不支持按未自动映射原因筛选。

### 15.3 工作表一：`待人工匹配`

可见列严格按以下顺序：

| 列 | 类型 | 说明 |
|---|---|---|
| Bangumi ID | 整数 | 只读参考 |
| 番剧名称 | 文本 | 优先 `name_cn`，缺失时使用 `name` |
| 放送日期 | 文本 | 数据库中的规范 `air_date` |
| 采集站 ID | 文本 | 人工填写；必须按文本保存 |
| 始集 | 正整数或空 | 人工填写 |
| 末集 | 正整数或空 | 人工填写 |
| 未自动映射原因 | 文本 | 导出时实时计算，只读参考 |

待匹配表不导出采集站标题、别名、年份、分集数或候选评分。

### 15.4 工作表二：`已有映射`

可见列严格按以下顺序：

| 列 | 类型 | 说明 |
|---|---|---|
| Bangumi ID | 整数 | 只读参考 |
| 番剧名称 | 文本 | 优先 `name_cn`，缺失时使用 `name` |
| 放送日期 | 文本 | 数据库中的规范 `air_date` |
| 采集站 ID | 文本 | 可修改；清空表示删除 |
| 采集站标题 | 文本 | 只读参考 |
| 始集 | 正整数或空 | 可修改 |
| 末集 | 正整数或空 | 可修改 |

已有映射表不导出 Bangumi 别名、采集站别名、年份或分集数。

### 15.5 工作簿元数据

工作簿包含不可见的技术元数据：

- 工作簿格式版本。
- 采集站 key。
- 每行稳定标识。
- 所属工作表和原始行号。
- 导出时的原始 `source_item_id`。
- 导出时的原始始集、末集。

元数据使用隐藏列或 `veryHidden` 元数据工作表保存，不干扰人工编辑。

采集站 ID 始终按文本读写，避免科学计数、精度截断并兼容未来字母 ID。

### 15.6 工作簿可用性

- 冻结表头。
- 启用自动筛选。
- 人工输入列使用一致的可编辑样式。
- 参考列使用只读提示样式。
- 合理设置列宽并对长名称换行。
- 导出前验证两个工作表可读且没有截断关键字段。

## 16. XLSX 差异识别

导入不要求人工填写操作类型。

### 16.1 待人工匹配

- `采集站 ID` 仍为空：忽略。
- 填写 `采集站 ID`：新增人工映射。
- 填写 ID 且始末集均空：一对一映射。
- 填写 ID、始集和末集：已完结分段。
- 填写 ID及始集、末集为空：开放末段。
- 只填写末集：失败。

### 16.2 已有映射

- 映射三字段均未改变：忽略。
- 修改采集站 ID或区间：替换映射。
- 清空采集站 ID：删除映射。
- 只修改标题、名称、放送日期等参考字段：忽略。

### 16.3 乐观并发检查

导入前比较数据库当前映射与工作簿隐藏的导出快照：

- 完全相同：允许处理。
- 数据库已经变化：该行报告冲突，不覆盖较新的修改。
- 待匹配行已经被建立映射：报告冲突。

导入不回写或修改原 XLSX 文件。

## 17. XLSX 导入原子性

### 17.1 普通修改

无跨行依赖的一对一新增、替换和删除按行独立事务提交。

单行失败不影响其他无关行。

### 17.2 关联分段组

导入器在校验前构建修改依赖组：

- 所有引用同一旧或新 `(source_key, source_item_id)` 的修改属于同一组。
- 如果一行连接两个采集站 ID，相关组继续合并，形成传递闭包。
- 删除旧一对一映射并新增多条分段映射属于同一组。

对关联组计算导入后的最终映射集合，再统一校验：

- 一对一独占。
- 分段均有始集。
- 区间不重叠。
- 开放分段最多一个且位于最后。
- 所有引用存在。

整组校验通过后在一个事务中提交；组内任一行无效则整组拒绝。

### 17.3 导入报告

命令结束时输出：

- 新增数量。
- 替换数量。
- 删除数量。
- 忽略数量。
- 冲突数量。
- 失败数量。
- 每个冲突或失败对应的工作表、行号和原因。

## 18. 模块边界

新映射域放入 `src/mappings/`：

```text
src/mappings/
  airDateEligibility.js
  titleNormalizer.js
  autoMatcher.js
  mappingRepository.js
  mappingService.js
  scheduleService.js
  mappingWorkbookService.js
  mappingRuntime.js
  config.js
```

### 18.1 `airDateEligibility`

- 校验 `air_date`。
- 判断日期精度。
- 以 `Asia/Shanghai` 判断已放送、未来精确日期或无法确认。
- 不访问数据库。

### 18.2 `titleNormalizer`

- 构建分级名称池。
- 解码、简繁、标点和数字规范化。
- 提取季度、Part/Cour 和作品形态。
- 不查询映射或写数据库。

### 18.3 `autoMatcher`

- 执行候选过滤、评分和双向唯一判断。
- 依赖事实查询接口和纯名称规范化接口。
- 不调用网络。
- 不直接写数据库。

### 18.4 `mappingRepository`

- 查询三张映射域表。
- 提供事务化写入原语。
- 集中维护跨行不变量和排除清理。
- 不计算标题相似度。

### 18.5 `mappingService`

- 编排自动一对一写入。
- 编排人工新增、替换和删除。
- 在写入前重新检查映射、占用和排除。

### 18.6 `scheduleService`

- 协调 Bangumi 最新详情与计划表。
- 执行每日和启动时到期计划。
- 不保存长期失败状态。

### 18.7 `mappingWorkbookService`

- 生成和读取 XLSX。
- 保存并验证工作簿元数据和快照。
- 识别行级差异和关联修改组。
- 不绕过 `mappingService` 直接写数据库。

### 18.8 `mappingRuntime`

- 连接 Bangumi 详情成功通知。
- 连接资源初始化和变化通知。
- 暴露给启动入口、调度器和 CLI 的稳定接口。

## 19. 错误处理与补偿

- Bangumi 或采集站事实数据先提交；后续自动匹配失败不回滚成功的外部数据采集。
- 自动匹配普通无结果只记录日志，不建立长期重试状态。
- Bangumi 每周详情刷新和采集站后续资源变化构成自然补偿。
- 到期计划在数据库异常或采集站未初始化时保留。
- 写入时发生并发占用返回 `skipped`，不覆盖已有映射。
- 人工 XLSX 普通修改逐行隔离；关联分段组整体隔离。
- 工作簿格式版本不支持、元数据缺失或采集站不一致时，在任何数据库写入前拒绝整个导入。
- 当前 `data/anime.db` 只用于只读分析和手工验证，测试与实现不得修改它。

## 20. 测试策略

### 20.1 日期测试

- `YYYY-MM-DD` 今天、过去和未来。
- `YYYY-MM` 过去、当前和未来年月。
- `YYYY` 过去、当前和未来年份。
- 上海自然日跨 UTC 日期边界。
- `0000-00-00`、空值和无效日期。
- 新有效日期覆盖旧值。
- 无效新值保留旧有效日期。
- 日期精确化、提前、推迟和降级后的计划协调。

### 20.2 名称测试

- HTML 实体。
- 全半角和标点。
- 简体与繁体。
- 罗马数字与阿拉伯数字。
- 季度相同、冲突和单侧缺失。
- Part/Cour 相同、冲突和单侧出现。
- 剧场版、OVA、特别篇和形态冲突。
- `总集篇/recap` 作为正式标题。
- `合集/全集` 比较变体。
- 主标题和别名分级。
- 别名数量不累计加分。

### 20.3 自动匹配测试

- 详情未完成时不匹配。
- 尚未放送时不匹配。
- 年份冲突硬拒绝。
- 年份缺失时只允许完整名称相等。
- 分集溢出硬拒绝。
- 双向唯一最佳。
- 两个方向的分差门槛。
- 任意一端被占用时跳过。
- 排除 ID 对时跳过。
- 写入前竞态导致安全 `skipped`。

### 20.4 映射仓库测试

- 一对一独占。
- 分段允许空档。
- 分段禁止重叠。
- 开放末段唯一且位于最后。
- 人工分段覆盖旧一对一映射。
- 人工删除后双方空闲时生成排除。
- 仍有分段占用时不生成排除。
- 任意一方建立新映射后清除过时排除。

### 20.5 触发集成测试

- Calendar 和搜索为每个有效 ID 登记详情。
- 详情成功后触发正向匹配。
- 资源详情首次成功后触发反向匹配。
- 标题、别名、年份和分集数量变化触发反向匹配。
- 已映射采集站 ID跳过反向匹配。
- 未来计划到期。
- 服务启动补处理过期计划。
- 采集站未初始化时保留计划。

### 20.6 XLSX 测试

- 两张工作表及固定可见列顺序。
- 采集站 ID 文本格式。
- 隐藏元数据和工作簿格式版本。
- 导出筛选和 `--include-upcoming`。
- 未修改行忽略。
- 待匹配行新增。
- 已有映射替换和删除。
- 参考字段修改不写数据库。
- 快照冲突不覆盖。
- 普通行失败隔离。
- 关联分段组整体原子。
- 导入报告包含工作表行号和原因。
- 工作簿渲染后表头、长标题和输入列可读。

所有自动化测试使用匿名临时数据库和固定真实风格标题样本。

## 21. 实施范围边界

本次实施包含：

- 三张新映射域表。
- 映射仓库和服务。
- 放送资格与一次性计划。
- 确定性自动匹配。
- Bangumi 详情成功和资源变化的双向触发。
- XLSX 人工审核导入导出。
- 对应测试和启动调度接线。

本次实施不包含：

- 从旧映射表迁移数据。

- 客户端修改。

完成本阶段后，新映射域可以独立产生可靠映射；下一阶段再让公开资源输出链消费该映射。
